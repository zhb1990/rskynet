Actor runtime anatomy

消息驱动Rust 运行时

rskynet 保留 skynet 的服务、邮箱、地址与 session 模型，用 Rust Future 承载服务内异步流程，并向上组合插件、QUIC 与可调试的强类型消息。沿着一次消息投递，读懂从业务 API 到工作窃取调度器的完整路径。

System layers

四层结构，一条统一的消息通道

内核只解决 Actor 身份、邮箱、调度和生命周期。时间、日志、网络乃至 QUIC 与跨节点能力都以服务形式接入；service 内插件则复用宿主邮箱，所以扩展能力仍服从同一种串行执行与消息语义。

Message anatomy

一次 request，实际跨过两条队列

服务邮箱保存外部消息，TaskSet 的就绪队列保存可继续 poll 的 Future。两者最终都被折叠为“这个服务现在可运行”，因此 RPC 回包、定时器和外部唤醒走同一套调度路径。

Typed extensions

消息可描述，service 也可继续拆分

过程宏现在不只按协议号分发：同一 MsgType 可以继续按 enum variant 路由，并从 Rust 类型生成请求/响应 Schema。大型 service 则能在保留一个地址与邮箱的前提下，按 namespace 装配多个插件。

强类型消息与 Dashboard

compile time → runtime inspection

  1. 01
    MessageSchema 派生结构

    #[derive(MessageSchema)] 直接读取字段，生成请求与响应描述，不依赖 Default 或手写样例。

  2. 02
    按 enum variant 路由

    #[msg(TYPE, variant = Command::Query)] 让一个协议号承载多种强类型命令。

  3. 03
    显式开放调试入口

    #[debug] 只把选中的 handler 注册到当前 service；默认不暴露在线调用。

  4. 04
    受控 send / call

    Dashboard 在 loopback 且 debug_console = true 时才允许提交 JSON，call 默认超时 10 秒。

Service 内组合式插件

one mailbox / multiple modules

  1. 01
    链接期收集

    插件描述符静态进入 inventory，并以 namespace + name 标识；配置决定每个 service 实例实际启用哪些插件。

  2. 02
    依赖排序与独立实例

    PluginHost 校验依赖后装配；同一插件类型在不同宿主中拥有各自状态。

  3. 03
    两种插件间通信

    需要返回值时直调类型化 Capability；无需等待的通知经 typed EventBus 回到宿主邮箱。

  4. 04
    复用 Actor 契约

    命令包装为 CommandEnvelope 后由宿主 dispatch，插件不会获得第二个地址、邮箱或并发执行权。

边界

service 仍是调度、故障与状态隔离边界；plugin 是同一 service 内的代码与依赖组织边界。namespace 不是 service 地址、注册名或 TOML section 名，EventBus 也不会绕过邮箱的串行执行保证。

Scheduler / full trace

从 push 到 park：调度器完整走一圈

调度不是“邮箱非空就找个线程”这么简单。它要同时守住三条约束：不丢任何一次唤醒、同一服务永远只有一个执行者、空闲 worker 不制造全场争抢。下面把消息进入、服务排队、worker 取活、Future poll 与睡眠唤醒连成一条完整路径。

生产者先写入工作

消息走 Mailbox::push_message；Waker 走 push_ready(TaskId)。两条队列都是无锁 SegQueue，必须先写数据再改变状态。

notify 决定是否递交服务

IDLE → QUEUED 返回 true，由本次生产者负责将 ServiceContext 放入 Scheduler；其他状态不会重复排队。

Scheduler 选择安置位置

有 searcher 时进 injector；有睡眠 worker 时定向 handoff；否则 worker 投本地 BWoS，外部线程投 injector。

worker 按优先级取服务

先收定向 handoff，再按周期检查 injector，然后取本地队尾，最后从其他 worker 队头窃取。

取出时标记 RUNNING

Scheduler::pop 先获得唯一 ServiceContext，再执行 mark_running。从这一刻起该 worker 独占服务内部状态。

run_service 逐件执行

优先处理初始化期间暂存消息，然后从 ready / message 两队列取 Work。Message 创建 Task；Ready(TaskId) poll Future 一次。

每 64 件检查是否让渡

若仍有其他服务排队或节点收工，返回 Yielded；否则预算清零，当前服务继续跑到真正空闲。

结束为三种结果

Idle 放生邮箱；Yielded 重排自己并切换服务；Dead 销毁任务、session、邮箱并回错误。

邮箱四态：防止丢活

one service / one owner

IDLE

不在运行队列，也没有 worker 持有。下一次投递者必须负责排队。

QUEUED

已经排在某条运行队列或 handoff 中，后续投递不能重复排队。

RUNNING

某个 worker 正独占执行服务，SvcCell 与 TaskSet 可无锁访问。

NOTIFIED

服务执行期间又有新工作；持有者结束前必须复位并重新扫描。

  • IDLE → QUEUED投递者 CAS 成功，然后进入 Scheduler。
  • QUEUED → RUNNINGworker 从运行队列取走并取得所有权。
  • RUNNING → NOTIFIED持有期间有消息或任务被唤醒，不再额外排队。
  • NOTIFIED → RUNNING两条队列看空时发现通知，复位后重新扫描。
  • RUNNING → IDLE队列为空且 CAS 成功，服务才真正放生。
  • RUNNING → QUEUED预算耗尽且别人等待，先改状态再重新入队。

worker 取活优先级

Scheduler::pop_runnable

  1. handoff slot别人点名递给当前睡眠 worker 的单槽 ServiceContext，不能被 pending 快速判空跳过。
  2. injector / every 64 pops即使本地队列持续有活，也周期性查看全局注入队列，防止外部工作饥饿。
  3. local.pop_back()owner 从自己的 BWoS 队尾取，完全无锁并保持缓存热度。
  4. injector.pop()接收非 worker 线程投递、本地队列溢出和收工时转存的服务。
  5. steal_front(victim)用 stealable 位图筛选受害者，随机起点，每轮最多尝试 2 个，避免 O(N²) 扫描。

空闲 worker

  1. searching++，最多自旋 256 轮
  2. 仍无工作则先登记 idle 位
  3. searching-- 并执行 SeqCst fence
  4. 睡前最后再 pop 一次
  5. 仍为空才 thread::park

两侧屏障保证至少一方看见对方：要么生产者看见 idle 位并唤醒 worker，要么 worker 的睡前复查看到新工作。早到的 unpark 会保留令牌，因此不会丢唤醒。

不变量

QUEUED / RUNNING / NOTIFIED 都表示服务已经“有人管”。只有从 IDLE 成功切到 QUEUED 的那次投递需要把服务加入 Scheduler；只有 worker 从队列取出并标记 RUNNING 后才能访问 SvcCell。这正是“每个服务串行，整个节点并行”的实现落点。

Runtime contracts

理解这三条，就理解了 rskynet

服务就是隔离边界

每个服务有独立地址、邮箱与任务集。业务状态属于服务，不在节点间共享。

Handle → Mailbox → Service

串行不是单线程

单个服务任意时刻只被一个 worker 执行；多个服务仍在可窃取线程池上并行。

one actor / one executor at a time

等待不会堵住 worker

request、sleep 与外部事件都挂起 Future；Waker 只让所属服务重新进入调度。

Pending → Ready(TaskId)
从一条消息，进入整个运行时。
