01 · 设计

skynet 的灵魂，一行不差地搬过来

skynet 的设计核心是三件事。rskynet 把这三件事逐一复刻，只把「Lua 协程」这一实现手段换成 Rust 的 Future。

01

服务即 Actor

每个服务有独立地址、独立邮箱，彼此只靠消息往来，内部天然单线程。服务实现 Service trait，状态放进 SvcCell，全程不需要锁。

02

两级消息队列

每服务一个邮箱，全局一个「有活干的服务」队列，N 个 worker 线程从中取活。邮箱状态机保证同一服务绝不被两个 worker 同时执行。区别是：两级队列都不加锁。

03

session 配对

call 分配一个 session 并挂起，回包带同一 session 回来时唤醒它。把协程换成 Future：session 对应 Waker，一句 .await 就是一次 call。

第三点是关键：Lua 协程只是实现手段，不是设计本身。把它换成 Future 之后，call、sleep、fork 的语义一字不差，而且不再需要嵌一个脚本虚拟机。

调度模型

可运行条件：邮箱非空，或，有就绪任务

rskynet 在 skynet 的基础上做了一处推广：服务的「可运行」条件从「邮箱非空」变成「邮箱非空 或 有就绪任务」。于是定时器回包、RPC 回包、外部线程唤醒三者走的是同一条路径，邮箱那一个状态机就同时管住了消息与 Future 唤醒。

投递方其它服务 · 定时器 · 唤醒
send / call 投递消息；时间轮回 RESPONSE；Future 被唤醒时入就绪队列。
服务上下文邮箱 + 就绪队列
状态从 Idle 变 Queued 时，由发起方负责把服务放进运行队列。
运行队列每 worker 一条 + injector
BWoS 块式工作窃取队列；非 worker 线程的投递与溢出走无锁 injector。
worker × N取一件活，就绪任务优先
优先 poll 就绪任务；消息按类型唤醒 session 或新开任务跑 dispatch。
1

取活

从运行队列取一个服务；取不到先自旋一会儿，还是空手才挂起。

2

干活

反复 take_work()：优先 poll 就绪任务，其次取一条消息。带 session 的 RESPONSE / ERROR 直接唤醒等待中的任务；其它消息开一个新任务跑 dispatch——等价于 skynet 新建一个协程。

3

让渡

每干满 64 件活（消息与就绪任务各算一件）回头看一眼运行队列：确实有别人在等才让渡，把自己交回队列；没人等就重新计数接着跑。

4

放生

邮箱和就绪队列都空了，状态落回 Idle，脱离运行队列，等下一次投递。

为什么「就绪任务优先于新消息」

这不是随便定的：它对应 skynet 里被 resume 的协程会一路跑到下一次 yield，之后才轮到下一条消息。就绪任务的语义就是「上一次没跑完、这次接着跑」，插队是它应得的。

monitor 死循环检测

每个共享 worker 各有一份 monitor 进度，rskynet-monitor 线程每 5 秒扫描一次。同一次 Future poll 连续跨过两个检查点仍未返回，就记录包含消息来源和目标 handle 的疑似死循环日志。只告警、不强杀；监控方可用 node.take_endless(handle) 读取并清除这个一次性标记。

02 · 内核深潜

消息路径上，为什么没有锁

C 版一条消息从发出到被处理要抢四把锁。这里逐层拆掉：邮箱、运行队列、唤醒、handle 表全部无锁化。

邮箱：无锁队列 + 四态状态机mq.rs · 对应 skynet_mq.c

C 版是「一把锁 + 环形缓冲 + 布尔量」，投递、取活、就绪任务全压在一把锁上。这里换成两条 crossbeam SegQueue 加一个原子状态机。

状态机是必须的：「队列已空」与「放生这个服务」必须原子地绑在一起，否则投递方压入新消息、看到标志仍为真于是不入队，消费方随后清掉标志放生——那条消息从此无人处理。四个状态把「持有期间来了新活」显式记下来。

01

投递方先压队列、再改状态。消费方一看到 Notified，复位重扫就一定捞得到东西，循环必然收敛。

02

入队方先改状态、再真的入队。反过来别的 worker 可能已把服务取走置成 Running，那一记 store 会把它标成「在队列里，实际谁也没拿着」，服务从此不再被唤醒。

03

销毁流程的最后一步才放生，且只有确认清理期间没有新活进来才算成功——两个 worker 同时清一个服务是不行的。

IdleQueued投递方 CAS 成功，由它负责入运行队列
QueuedRunningworker 从运行队列取到，开始独占执行
RunningNotified持有期间又来了新活，投递方无需入队
NotifiedRunning消费方复位后重扫队列，必有收获
RunningIdle两条队列都空，CAS 成功才算放生
RunningQueued让渡：先改状态再入队

运行队列：BWoS 工作窃取bwos.rs · 移植自 stdexec

全局队列换成一 worker 一条的 BWoS 块式工作窃取队列：owner 在自己的队列上 push / pop 不需要任何锁，闲下来才去别人队列头部窃取。

  • 环形缓冲切成块：owner 只碰当前块，窃贼只碰已交出的旧块，常态零同步，跨块才 CAS 一次（摊薄到每 16 个元素一次）。
  • 本地队列后进先出：刚投递的服务多半还热在缓存里。
  • 非 worker 线程的投递与写满溢出走无锁 injector 兜底；worker 每取 64 次活回头看一眼 injector，防饿死。

唤醒：位图点名，不吵别人空闲位图 + 定向 unpark + handoff

投递方与 worker 构成 Dekker 模式（各有一个全序点），唤醒才不丢：

  • worker 侧先登记再扫：fetch_or 进空闲位图，然后才扫队列；扫到活清位干活，扫不到才 park。
  • 投递侧先入队再看：读位图，非零就 CAS 清位、unpark 那个具体的 worker——取位图最低位，稳定偏好编号小的线程。
  • searching 计数：有人醒着扫队列就不再叫第二个，扇出场景唤醒从 O(消息数) 压到 O(1)。
  • handoff 单槽：活直接递到被唤醒者手上（BWoS 里 owner 正在写的那块对窃贼隐形），槽被占才回退 injector。
  • 睡前先自旋几轮：接住「晚了半微秒」的投递，省一次挂起加唤醒。

让渡：按争用情况决定没有权重表

C 版的 worker 权重表这里没有照搬——它的前提是全局 FIFO 队列，换成每 worker 一条窃取队列之后前提就没了。统一改成一条规则：

  • 干满 64 件活，问一次「运行队列里有人在等吗」，有就让渡，没有就接着跑。
  • 没人等时行为与「一口气干到邮箱空」一致，多付的只是每 64 件一次原子读。
  • 消息与就绪任务各算一件：只数消息的话，一个在 poll 里唤醒自己再挂起的任务会让就绪队列永远非空，节点再也关不掉。
  • 收工信号也算「该让渡了」——那是这类任务唯一的出口。

窃取：位图挑受害者别扫全场

原来的「随机起点加环形扫满所有 worker」，22 核上一个空闲 worker 最坏要读 21 条队列头，全部空闲时就是 O(N²) 的跨核缓存流量。

  • stealable 位图：位 i 表示 i 号 worker 有已交出的整块可偷。owner 跨块时置位（每 16 个元素一次，摊薄可忽略），窃贼偷空清位。
  • 窃取从 O(N²) 变成「读一个字、挑一位」。
  • 两道限流：并发窃取者不超过 max(1, worker/2)，单轮最多试几个受害者，失败就回退到看 injector、自旋、park。

monitor 死循环检测monitor.rs · 对应 skynet_monitor.c

worker 在每次 poll Future 的前后推进版本号；同一次 poll 连续跨过两个检查点仍未返回，就记录包含消息来源和目标 handle 的疑似死循环日志。

  • 只告警，不强杀线程或节点。
  • 监控方用 node.take_endless(handle) 读取并清除一次性标记，对应 skynet.stat("endless")。
  • 监测边界是共享 worker 上的单次 Future poll；独占服务线程与启动期同步初始化不在其中。
03 · 独占线程的服务

「独占一条线程」是服务的一种运行方式

服务默认跑在共享的 worker 池上，也可以让它独占一条线程。C 版为定时器与 socket 各写了一条专用线程——它们不是服务，没有邮箱也没有地址，内核得单开一套代码。这里换个思路：日志、定时器、网络层都只是普通服务，只是各占一条线程。

维度共享服务独占服务
谁来执行 运行队列上的某个 worker，可能被窃取 自己那条线程，从不进运行队列
没活干时 去找别的服务干，找不到才挂起 调服务自己的 idle 钩子
有活投进来 邮箱入运行队列，按空闲位图点名叫一个 worker unpark 那条线程，再调一次 interrupt
适合什么 业务服务：launch 一万个只是一万个邮箱 要阻塞在自己事件源上（epoll）、或要按节拍醒来（时间轮）的活
fn idle(&self, ctx, idler)

邮箱与就绪队列都空了时调用

跑在自己那条线程上，可以放心阻塞。默认实现是 idler.park()；定时器在这里推一格时间轮再 park_timeout(2.5ms)；网络层在这里 poll.poll(events, None)，顺手把 IO 事件转成消息投出去。

fn interrupt(&self)

从任意线程把上面的阻塞叫醒

默认空实现——内核每次唤醒都会先 unpark 再调 interrupt，所以纯消息驱动的服务（日志）什么都不用写；阻塞在别处的服务在这里敲自己的唤醒手段（mio 的 Waker）。

一条硬要求：interrupt 必须接得住早到的唤醒

唤醒可能发生在线程真正睡下去之前，那一下不能丢，否则「取活取空」与「睡下去」之间的那次投递就没人管了。std 的 park 令牌与 mio 的 Waker 都满足，Condvar 不满足。

退出时序上，独占线程的退出条件是自己被摘除而不是节点收工——这样日志服务「留到最后收尾」的语义原样保住：节点收尾时先送走普通服务、join 掉它们的线程，最后才摘除保留服务。而发现自己已死之后，那条线程会先把邮箱里积压的消息处理完再销毁，关停前最后几行日志不会丢。

04 · 为什么服务状态可以不加锁

调度器保证：同一服务任意时刻只被一条线程执行

这条不变量由邮箱的四态状态机维持：只有 Queued 变 Running 这一次取出的人才有执行权。服务内部天生是单线程访问的，只是「哪条线程」会随调度变化。换成工作窃取之后照旧：一个服务同一时刻只躺在一条队列的一个槽位里，被偷走也只是换了个 worker 执行。

SvcCell<T> 就建立在这条不变量上：它本质是 RefCell，只额外声明了 Sync，好让 Arc<MyService> 满足 Send。用它而不用 Mutex 是有意的——跨 await 持有 Mutex 会真的死锁，而 SvcCell 只会在借用冲突时 panic，第一时间把 bug 暴露出来。

内核自己也吃这条不变量：任务集（Slab<TaskSlot>）与 SessionTable 都是 SvcCell，不再有锁。CURRENT_SERVICE 线程局部量记着「本线程此刻在跑哪个服务」；call / sleep / spawn 等 service 本地接口会强制校验它，从外部 OS 线程调用会立即 panic。

rust
struct Counter { hits: SvcCell<u64> }

*hits.borrow_mut() += 1;      // 没有锁，没有原子操作

需要长期交给外部线程时只导出 NodeRef（投消息、管理节点、抓取 NodeStats / ServiceStats 近似快照），或用 ReplyToken 完成一次外部请求。任务数、session 数、消息数与 CPU 时长都由原子量镜像，观测线程不会碰 SvcCell。

05 · 内置服务

一个都不在内核里，各是一个独立 crate

日志、定时器、引导在 C 版都是内核的一部分，这里全部搬出来：与网络层走同一条接入路子——用 Registry 注册类型，在配置里占一段，要独占线程就用 with_exclusive。图的和网络层拆出去是同一件事：内核不碰系统调用。

rskynet-logger默认启用

日志服务

一个独占线程的服务。积压超过 max_queue 丢旧保新，回落后先写一条丢弃汇总；控制消息不会被丢弃。

rskynet-timer默认启用

分层时间轮

256 格近期轮加 4 层 64 格，精度 10ms。记账（WheelTimer）与推刻度（TimerService）分家：引导期间挂的表一条不丢。

rskynet-bootstrap默认启用

引导服务

按清单顺序拉起业务服务，逐项等待目标 init 完整返回；初始化期间 RPC、timer 与 IO 回包仍可推进，普通消息按 FIFO 暂存。

rskynet-signal默认启用

信号与崩溃报告

SIGINT / SIGTERM 等默认优雅关停，属性宏可覆盖；独立进程的 minidump 加堆栈崩溃报告，panic 与原生崩溃都落盘。

rskynet-netfeature "net"

TCP / UDP 网络层

一个独占线程的服务：槽位状态机、高低水位背压、域名解析。对应 socket_server.c，但内核因此不碰 epoll / kqueue。

rskynet-tlsfeature "tls"

双向 TLS

基于 rustls、复用网络层，把 TLS 驱动成一个普通 actor 服务。支持系统根、Mozilla 根、自定义根与带密码的 PKCS#8 私钥。

rskynet-httpfeature "http"

HTTP/1.1 客户端与服务端

基于 ureq-proto 的 Sans-IO 状态机：共享连接池客户端 actor 与可嵌入服务端，keep-alive、chunked、100-continue、流式 body、超时与背压齐备。

rskynet-dashboardfeature "dashboard"

节点 Dashboard

页面与 /api/v1/stats 直接嵌入可执行文件，部署零静态资源。服务 / 网络标签展示节点、service 与活跃 socket 统计与短期趋势。

rskynet-clusterfeature "cluster"

跨节点通信

节点间 Protobuf 通信，消息 TYPE_ID 与 handler 由宏提交到链接期自动注册表。跨节点边界序列化，本地转交仍走 Payload::Boxed 零拷贝。

rskynet-macros默认启用

过程宏

service / exclusive 生成 trait 实现；msg 按协议号路由并通过 FromPayload 取参数；signal 覆盖默认信号行为。

#[rskynet::service]
impl Calculator {
    async fn init(&self, ctx: Ctx) -> Result<()> {
        ctx.register_name("calculator");
        Ok(())
    }

    #[msg(MsgType::USER)]
    async fn add(&self, ask: Add) -> Sum { Sum(ask.0 + ask.1) }

    #[msg(default)]
    async fn other(&self, _ctx: Ctx, _msg: Message) {}
}

有返回值且发送方在等待时会自动回包；自定义对象用 boxed_payload!(Ask, Answer) 声明负载转换。

rust · cluster
#[derive(Clone, PartialEq, prost::Message, ClusterMessage)]
#[cluster(type_id = 1001)]
struct PingRequest {
    #[prost(uint64, tag = "1")]
    round: u64,
}

#[rskynet::cluster::handler("pong")]
async fn pong(remote: RemoteContext, ping: PingRequest)
    -> Result<PongResponse, String> {
    remote.request("pong-worker", Payload::of(ping)).await
        .map_err(|e| e.to_string())?
        .downcast::<PongResponse>()
        .map(|r| *r)
        .map_err(|_| "pong-worker 返回了错误的负载类型".to_owned())
}

RemoteContext 提供自动附带路由、TYPE_ID、来源节点与请求 ID 的日志；跨节点边界用 Protobuf，本地转交不重复序列化。

07 · 快速上手

一个 echo 服务，就是全部

日志、信号、定时器、引导这些内置服务由 rskynet::start 按 feature 自动挂上，业务代码只写这一份。

rust
use rskynet::{Config, ConfigExt, Ctx, Message, Registry, Result};

struct Echo;

#[rskynet::service]
impl Echo {
    async fn init(&self, ctx: Ctx) -> Result<()> {
        ctx.register_name("echo");
        Ok(())
    }

    async fn dispatch(&self, ctx: Ctx, mut msg: Message) {
        let payload = msg.take_payload();
        let _ = ctx.reply(&msg, payload);
    }
}

fn main() -> Result<()> {
    let registry = Registry::new().with("echo", || Echo);
    let config = Config::default().with_bootstrap(["echo"]);
    rskynet::start(config, registry)
}

读表的方法

第二行是这轮改造的主要目标，也是收益最大的一处（4.4 倍）：原先 16 个 worker 抢一把 Condvar、轮流被无谓唤醒又空手而归，吞吐反而只有四线程时的六分之一；现在靠自旋接住迟到的投递、靠 searching 不叫第二个人起来、靠 handoff 把活直接递到手上，这条退化基本填平了。

第三行看不出差别：单服务吞吐压的是「一个 worker 反复取自己邮箱里的消息」，本来就没有竞争。它的意义在于确认没有回退——邮箱那套状态机比原先的布尔量多了几次 CAS，值得盯一眼。

call 一个来回（4 worker，debug 构建）加锁版与无锁版都是约 6µs。这台机器的读数有 ±10% 的抖动（睿频与散热），数字均为交替测五轮取中位数。压测跑法：cargo test --release -- --ignored --nocapture。

09 · 现状与工程结构

已实现 / 未实现 / 相对 C 版的改动

01全局队列换成每 worker 一条的窃取队列

BWoS 加 injector 兜底，owner 侧操作零锁。

02专用线程改成独占线程的服务

定时器线程与 socket 线程不再是内核里的独立代码，而是各占一条线程的普通服务。

03内置服务全部搬出内核

日志、信号、定时器、引导各是一个独立 crate；时间也随定时器一起搬走，内核只留一个必须注入的 Timer 抽象。

04投递即唤醒

C 版靠定时器线程每 2.5ms 顺手唤醒，最坏要等一个 tick；这里投递方按空闲位图点名叫一个具体的 worker，延迟更低。

05消息路径上没有锁

邮箱与 injector 是无锁队列，唤醒是位图加 park / unpark，handle 表与名字表用 arc-swap 做快照读；挂定时器也不再抢时间轮的锁。

06节点不再是全局单例

收进 Arc<Node>，同进程可以跑多个互不干扰的节点，单元测试因此能并行。

07字符串命令表换成类型化方法

skynet_command("LAUNCH", ...) 这类接口改成 Ctx 上的方法，编译期就能查错。

08消息负载可以是任意 Rust 对象

同进程传递走 Payload::Boxed，零拷贝、不需要序列化；Payload::Bytes 为跨节点序列化保留字节流表示。

跨平台

因为内核不碰 epoll / kqueue、不碰文件 IO、不碰系统时钟，目前是纯跨平台的：Windows 上可以直接 cargo run。源码按 skynet-src 的文件名组织（message.rs、mq.rs、server.rs、monitor.rs……），方便与 C 版逐一比对。
